工程项目复盘：从 Demo 到可审计系统

发表于2026-06-17|更新于2026-08-13|Engineering
|浏览量:

招聘 Agent、图记忆 RAG、文献挖掘、交互式工具和数据系统看起来相差很远，但它们在工程上会遇到同一个问题：一个 Demo 如何变成可审计、可复现、可交接的系统？

把这些项目放在一起复盘后，我发现真正拉开差距的往往不是模型本身，而是状态、边界、失败处理和验证方式。

Demo 的价值和局限

Demo 的价值是快速证明一件事能跑通。但 Demo 通常有几个隐患：

  • 输入样本太少。
  • 成功路径被硬编码。
  • 失败状态没有处理。
  • 数据无法追溯。
  • 写入操作没有保护。
  • 评估只靠观感。

AI 项目尤其容易被 demo 欺骗。一次漂亮回答不代表系统稳定，一次成功调用不代表流程可交付。

可交付系统需要哪些层

从这些项目里，我总结出一个最小闭环：

  1. 数据层：输入、输出、中间产物、ID、版本和存储位置清楚。
  2. 流程层：每一步的前置条件、后置状态和失败处理清楚。
  3. 模型层：LLM、embedding、rerank、GNN 等组件职责清楚。
  4. 工具层：脚本、CLI、API、runbook 能重复执行。
  5. 审计层：日志、Agent Runs、决策依据、人工确认记录齐全。
  6. 安全层：写入白名单、confirm、scope guard、redaction。
  7. 评估层：指标、样本、错误类型和回归检查稳定。

一个项目如果缺少这些层，往往还能演示，但很难交接。

招聘 Agent 的系统化经验

bytedance/ 的 HireLoop 是最典型的工程闭环项目。它不是一个“自动筛简历”的黑盒，而是基于飞书 Base 的招聘运营辅助系统。

它有几个值得复用的设计：

  • 7-Agent 虚拟组织分工明确。
  • 业务状态机限定 Agent 只能推进到 decision_pending。
  • offer / rejected 必须由人类确认。
  • 写回真实 Base 需要双确认和 planNonce，防止 TOCTOU 问题。
  • Agent Runs 记录审计信息，但不记录完整思维链或简历原文。
  • Graph RAG 只提供结构化摘要，不把 raw evidence 直接塞进 provider prompt。

这说明高风险 AI 系统不是“模型越自动越好”，而是要把边界画清楚。

图记忆比赛项目的推进节奏

competition/ 的周期总结记录了一个从模糊想法到工程原型的过程：

  • 第一阶段先收敛方向：招聘场景、岗位内局部图、Graph-RAG first。
  • 第二阶段打通工程闭环：LLM 抽取、画像落表、embedding 建边、projection、Reviewer/Search RAG。
  • 第三阶段扩大规模：从 1000+ 到 3000，再到 6000+ 候选人快照。

这个节奏很值得复用：先收敛系统主线，再扩规模，再加模型增强。否则一开始就同时做全局图、GNN、图数据库、飞书自动化和复杂 Agent，很容易散掉。

文献挖掘项目的可复现经验

project/ 和 reproductive-ai-mining-assignment/ 的核心价值是可复现。它们把“搜论文”拆成白名单、召回、合并、规则筛选、大模型复核和导出报告，每一步都有脚本和中间文件。

这类任务最怕最终只有一个 CSV。可复现项目应该回答：

  • 数据从哪里来？
  • 为什么这些候选被召回？
  • 为什么这些候选被排除？
  • 规则和 LLM 分别做了什么？
  • 如果明天重跑，会得到什么差异？

工具化项目的启发

guizang-ppt-skill-main/ 和 vibe-vibe-main/ 更偏工具与方法论。它们提醒我：好的工具不只是代码，还包括使用约束、模板、参考、检查清单和输出规范。

比如一个 PPT skill 如果只有 HTML 模板是不够的，还需要：

  • 主题风格约束。
  • 版式组件。
  • 图片提示词。
  • 截图检查方法。
  • 导出和验证流程。

工具的本质是把经验固化成可重复执行的流程。

我会继续保留的工程习惯

  1. 先写系统边界，再写功能。
  2. 所有长任务支持 checkpoint 和 resume。
  3. 所有派生数据保留源 ID。
  4. LLM 输出尽量结构化，再进入下游。
  5. 写入真实系统默认关闭，执行前显式确认。
  6. Demo seed 和真实数据路径分开。
  7. 用 runbook 描述端到端流程。
  8. 把失败路径当成一等公民。
  9. 不把高风险决策交给 Agent 自动完成。
  10. 把项目经验整理成文档、模板和脚本。

工程化不是把代码写复杂，而是让系统在输入变化、环境变化、人员交接和失败恢复时仍然可控。
