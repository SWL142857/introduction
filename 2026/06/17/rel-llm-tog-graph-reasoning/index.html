Rel-LLM 与 ToG：关系表上的图推理路线

发表于2026-06-17|更新于2026-08-13|Research
|浏览量:

关系数据库本身就是一种图。表是节点类型，行是实体，外键是边，时间戳提供演化顺序。Rel-LLM 和 ToG-style reasoning 的核心问题是：能不能让大模型在这种结构上做可解释的预测，而不是只把表格拍平成文本。

这里比较两条路线：一条用 GNN 压缩关系结构，再把表示交给 LLM；另一条让模型显式选择关系、搜索实体并保留推理路径。它们的差别不仅是精度，也包括成本、延迟和解释方式。

Rel-LLM 的基本思路

Rel-LLM 面向 RelBench 这类关系学习任务。它把多表数据库构造成异构实体图，然后在预测时间点采样 temporal-aware subgraph，再用 GNN 或 LLM 进行推理。

传统路线是：

  1. 从关系表构造 heterogeneous entity graph。
  2. 按时间点采样相关子图。
  3. 用 GraphSAGE 等 GNN 编码结构。
  4. 将图表示投影到 LLM 空间。
  5. 用 JSON prompt 或 soft prompting 让 LLM 输出分类/回归结果。

这条路线的优点是效率高、可训练、和传统图学习兼容；缺点是解释性不一定强，GNN 表示经过压缩后，模型到底用了哪些关系和实体并不总是清楚。

ToG-style reasoning 的替代路线

ToG 的思路更接近“显式探索”。它不先把图压成向量，而是让 LLM 逐跳选择关系、搜索实体、评分、剪枝，并判断当前证据是否足够。

迁移到 Rel-LLM 后，主循环大致是：

  1. RelationPruner：从当前实体可走的外键关系里选出最相关的关系。
  2. EntitySearcher：沿关系在 HeteroData / edge_index 中找到候选实体。
  3. EntityScorer：根据任务上下文给候选实体打分。
  4. EntityPruner：保留前沿实体和实体链。
  5. SufficiencyReasoner：判断已有三元组是否足够预测。
  6. PredictionGenerator：生成分类标签或回归值。

这等于是把“图推理路径”变成一串可检查的实体链。

三种剪枝工具

设计里支持三种关系/实体筛选方式：

  • llm：语义理解最强，成本最高，稳定性依赖 prompt。
  • bm25：便宜、快、可复现，适合文本字段比较明确的场景。
  • sentencebert：比 BM25 更语义化，比 LLM 更便宜，但需要 embedding 模型。

这给了一个很实用的工程策略：先用 BM25 或 SentenceBERT 过滤，再把少量候选交给 LLM 做最终判断。纯 LLM 探索很漂亮，但在大图上容易被成本和延迟拖垮。

关系表图推理的关键难点

关系表不是普通知识图谱，它有几个特殊问题：

  • 行实体通常缺少自然语言名称，需要从关键列生成文本表示。
  • 外键边有方向，forward 和 reverse 的语义不同。
  • 时间很重要，不能把预测时间之后的信息泄漏进去。
  • 数值列、类别列、文本列需要不同序列化方式。
  • 回归任务比问答任务更难解释，因为答案不是一个实体名。

所以 ToG 不能照搬到数据库上，必须加上表结构、任务元数据和 temporal constraint。

GNN 路线和 ToG 路线怎么选

我的阶段性判断是：

  • 如果目标是 benchmark 性能和训练效率，GNN + LLM 更稳。
  • 如果目标是解释路径、debug 数据泄漏、生成可读证据链，ToG-style 更合适。
  • 如果任务很大，可以用 GNN 或 embedding 做候选收缩，再用 ToG 做局部解释。

这其实和 GraphRAG 很像：向量/模型负责快速缩小范围，显式图探索负责解释和多跳结构。

可继续写的研究问题

后续这条线还可以继续展开：

  • 如何自动选择每个表的关键列，生成更好的实体文本？
  • 如何避免 ToG 探索中的时间泄漏？
  • 如何把 ToG 产生的路径作为 GNN 的可解释监督？
  • 如何评估关系推理路径是否真的有用，而不是事后合理化？
  • 如何在分类和回归任务之间统一 PredictionGenerator？

关系数据库上的 LLM 推理很有潜力，因为企业数据天然以表和外键存在。真正有价值的系统，应该能在表结构里走路，而不是只把表格转成一大段 prompt。
