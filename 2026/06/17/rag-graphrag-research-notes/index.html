RAG 到 GraphRAG：我的检索增强生成研究笔记

发表于2026-06-17|更新于2026-08-13|Research
|浏览量:

RAG 的朴素版本很容易理解：先检索，再生成。但真正做复杂问答时，会很快遇到几个问题：检索证据不完整、问题需要多跳推理、文档结构被分块破坏、模型把局部证据拼成错误答案、评估指标无法解释失败原因。

把基础管线、多跳问答、推理树、GraphRAG 与效率实验放在一起，可以看见一条清楚的升级路线：先让系统工程可用，再让中间过程可检查，最后让结构真正参与检索与推理。

基础 RAG：先把管线做完整

RAG 的基础管线可以拆成五步：

  1. 数据加载：PDF、Markdown、网页、表格、JSONL 等不同来源进入统一文档表示。
  2. 文本切分：chunk size、overlap、句子边界、标题层级和元数据一起决定召回质量。
  3. 向量索引：embedding 模型、向量库、距离函数和索引参数决定检索效率。
  4. 检索增强：query rewriting、hybrid search、rerank、Top-K 策略影响证据质量。
  5. 生成评估：答案格式、引用证据、失败案例和指标决定系统是否可信。

这部分最容易踩的坑是过早追求“高级框架”。如果数据切分混乱、元数据缺失、评估集不稳定，再复杂的 Agentic RAG 也只是把错误包装得更精致。

多跳问答：问题不是检索一次能解决的

HotpotQA、2WikiMultihopQA、MuSiQue 这类任务的难点在于答案需要跨多个事实节点。普通 Top-K 检索经常只召回其中一跳，于是生成模型要么猜，要么把无关证据硬连起来。

LoCoRAG/ 的管线更强调多步执行：

  • 检索服务提供统一 /retrieve 接口。
  • RAG pipeline 负责多步 query、事实抽取和答案生成。
  • 批量预测脚本支持断点续跑。
  • 评估脚本同时计算 EM、F1、cover EM、ROUGE-L 和 LLM judge。

这种结构的好处是把“检索器”和“推理器”解耦。检索器只负责给候选证据，推理器负责决定是否继续查、如何重写问题、如何聚合答案。

RT-RAG：把问题拆成推理树

RT-RAG/ 的核心思想是把复杂多跳问题显式拆成二叉推理树。树里的节点对应子问题，叶子节点面向更局部的事实检索，内部节点负责组合和改写。

我觉得这个方法的价值在于两个词：显式和自底向上。

  • 显式：把“模型脑中隐含的分解”外化成结构，方便检查和调试。
  • 自底向上：先解决局部子问题，再合成上层答案，减少一次性推理的漂移。

从工程角度看，树状 RAG 也带来新问题：树怎么生成、错误分解如何纠正、多个候选树如何选择、每个节点检索多少证据才合适。这些问题不能只靠 prompt，要配合评估和可视化。

GraphRAG：让结构参与检索和推理

GraphRAG 的关键不是“把文档变成图”这么简单，而是让图结构真正改变检索路径。一个有用的 GraphRAG 系统至少要回答：

  • 实体和关系怎么抽取？
  • Schema 是固定的、演化的，还是弱约束的？
  • 图中有哪些层：实体、关系、关键词、社区、摘要？
  • 查询如何落到子图，而不是全图漫游？
  • 图证据如何进入生成模型？

youtu-graphrag/ 给了一个很好的方向：Schema 引导的层次化知识树、结构语义双重感知的社区检测、Agentic Decomposer、迭代检索和统一配置。它强调跨领域迁移时减少人工干预，也强调成本和精度的 Pareto 改进。

这里的重点是：图不是为了炫技，而是为了把知识组织成可导航结构。实体图、社区摘要、关键词索引和子问题分解需要协同工作。

评估：别只看一个 F1

RAG 评估最危险的地方是只看最终答案。一个错误答案背后可能有很多原因：

  • 问题分解错了。
  • 检索没有召回关键证据。
  • 召回了证据但 rerank 排太后。
  • 生成模型忽略了证据。
  • 答案表达和标准答案不一致。
  • LLM judge 本身不稳定。

所以我更喜欢把评估拆成几层：

  • Retrieval recall：关键证据有没有出现。
  • Cover EM：答案所需证据是否被覆盖。
  • Answer F1 / EM：最终答案是否匹配。
  • LLM accuracy：语义是否正确。
  • Case analysis：失败案例属于哪一类。

result analysis/ 和 Efficiency/efficiency_experiment/ 中的 summary 文件，正好可以继续发展成一套 RAG 评估模板。

我的阶段性判断

RAG 的发展可以理解为三次升级：

  1. 从“把文档塞给模型”升级到“可检索的外部知识库”。
  2. 从“单次检索”升级到“多步检索和问题分解”。
  3. 从“向量相似度”升级到“结构化图导航和可解释证据链”。

未来继续做这条线时，我会优先关注三个问题：

  • 如何让图构建更便宜、更稳定？
  • 如何让多跳检索的中间状态可检查？
  • 如何建立能解释错误来源的评估体系？
